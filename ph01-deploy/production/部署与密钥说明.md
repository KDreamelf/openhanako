# 幻宙01（phantasm 01 / PH01）三端 Docker 部署与密钥说明

本目录用于生产部署三个容器：

`PH01` 是仓库路径、镜像名和容器名使用的路径安全代号；产品正式名称为 `phantasm 01`，中文名为 `幻宙01`。

- `ph01-auth-center`：认证中心，公网端口 `8080`，内部 mTLS 端口 `8443`。
- `ph01-ai-gateway`：魔改 New API 网关，公网端口 `3000`。
- `ph01-experience-network-manager`：经验网络管理端，端口 `8090`；同一个程序内包含经验包管理、主脑审核入口、主控证书签名治理能力。

三端都会加入 `ph01-internal` Docker 内网。容器之间固定用服务名互联，目标写在配置文件里，不写死到代码：

| 调用方 | 目标服务 | 配置内地址 |
|---|---|---|
| AI 网关 | 认证中心 mTLS 端口 | `https://ph01-auth-center:8443` |
| 认证中心 | AI 网关内部同步接口 | `http://ph01-ai-gateway:3000` |
| 主脑 / 管理脚本（同机容器） | 经验网络治理端 | `http://ph01-experience-network-manager:8090` |

反代访问端口已在 `docker-compose.yml` 预置。默认绑定 `0.0.0.0`，用于给 Nginx / 1Panel 等反代访问；服务自身仍是 HTTP，不建议让终端用户绕过 HTTPS 反代直连：

| 服务 | 宿主机端口 | 用途 |
|---|---:|---|
| 认证中心 | `0.0.0.0:18080` | 客户端注册 / 登录 / 管理端页面 |
| AI 网关 | `0.0.0.0:13000` | 用户网页、API 网关入口 |
| 经验网络管控 | `0.0.0.0:18090` | 主脑不在同机容器时的治理端入口 |

如果宿主机端口已被占用，可以在执行部署脚本时覆盖端口：

```bash
PH01_AUTH_HOST_PORT=28080 PH01_AI_HOST_PORT=23000 PH01_EXPERIENCE_HOST_PORT=28090 ./deploy.sh --build
```

`PH01_BIND_ADDR` 默认是 `0.0.0.0`。如果反代和 PH01 部署在同一台宿主机，并且不希望外部网络直连这些 HTTP 端口，可以执行部署时覆盖成 `127.0.0.1`。

应用容器内部监听仍保持 `0.0.0.0`，程序监听端口不变；这里改变的只是 Docker 发布到宿主机时的绑定 IP。

编排里没有 PostgreSQL / Redis 容器。数据库和 Redis 连接都写在顶层持久化目录的配置文件里：

- `data/production/config/auth-center.hcl`
- `data/production/config/ai-gateway.yaml`
- `data/production/config/experience-hub.json`

## 直接部署

如果你没有自己的 Docker 镜像仓库，并且准备把源码目录传到服务器现场构建，服务器目录保持：

```text
ph01_client/
  data/production/
    config/
    certs/
    runtime/
    logs/
  ph01-ai-gateway/
  ph01-backend/
  ph01-experience-hub/
  ph01-deploy/production/
```

然后执行本机构建部署：

```bash
cd ph01-deploy/production
chmod +x deploy.sh build-images.sh scripts/generate-mtls-certs.sh
./deploy.sh
vim ../../data/production/config/auth-center.hcl
vim ../../data/production/config/ai-gateway.yaml
vim ../../data/production/config/experience-hub.json
./deploy.sh
```

裸跑 `./deploy.sh` 贴近源码上传部署模式：如果 `data/production` 没有初始化文件，脚本只生成持久化配置、证书、运行目录并退出，等待你先修改正式配置；如果 `data/production` 已存在，脚本不会自动补齐或覆盖其中的文件，而是本机构建镜像并启动 Compose。

`--build` 会在服务器本地构建三个镜像，镜像 tag 默认仍使用 `registry.example.com/ph01/...:20260505`。这只是本地镜像名，不会访问镜像仓库；compose 会直接使用本地已构建镜像。

如需换成本地更好辨认的镜像名前缀，可以这样执行，脚本会同步注入给 Compose：

```bash
./deploy.sh --build local/ph01 20260505
```

如果是从开发机压缩上传源码目录，先清理本地依赖和构建缓存，避免把 `node_modules`、Go build cache、旧二进制一起打包：

Windows PowerShell：

```powershell
cd ph01-deploy/production
.\scripts\clean-upload-artifacts.ps1
```

Linux / WSL：

```bash
cd ph01-deploy/production
chmod +x scripts/clean-upload-artifacts.sh
./scripts/clean-upload-artifacts.sh
```

如果你之后有镜像仓库，可以先构建并推送，再在服务器只拉镜像部署：

```bash
cd ph01-deploy/production
chmod +x deploy.sh scripts/generate-mtls-certs.sh
./deploy.sh --pull
```

`deploy.sh --pull` 会在已有 `data/production` 时执行：

```bash
docker compose pull
docker compose up -d --remove-orphans
```

默认持久化目录是 `ph01_client/data/production`。如果服务器上要放到别的位置，可以设置：

```bash
export PH01_DATA_DIR=/srv/ph01/data/production
```

首次执行 `./deploy.sh` 时，脚本会把 `ph01-deploy/production/config` 和 `ph01-deploy/production/certs` 中的预置文件复制到 `data/production`，然后退出。编辑 `data/production/config` 里的正式配置后，再执行 `./deploy.sh`。如果你明确只想补齐缺失初始化文件，可以使用 `./deploy.sh --init-data`；若目标文件已存在，绝不覆盖。

部署前主要改这些位置：

- `docker-compose.yml`：镜像前缀和 tag 默认由 `PH01_IMAGE_REGISTRY`、`PH01_IMAGE_TAG` 控制；现场构建模式不用手动改。
- `../../data/production/config/auth-center.hcl`：改认证中心 PostgreSQL、Redis、SMTP、域名。
- `../../data/production/config/ai-gateway.yaml`：改 AI 网关 PostgreSQL、Redis、公开域名。
- `../../data/production/config/experience-hub.json`：改经验包存储目录、管理 token、CORS、主控证书配置。

`auth-center.hcl` 和 `ai-gateway.yaml` 里的 PostgreSQL DSN 不能保留 `CHANGE_ME_*` 或 `postgres.example.internal`；部署脚本会在启动容器前拦截这种模板值。认证中心启动时必须连上 PostgreSQL，否则会直接退出并导致 `ph01-auth-center` unhealthy。

如果 `docker compose up` 失败，`deploy.sh` 会自动打印三个 PH01 容器的状态、healthcheck 输出和最近日志。`ph01-auth-center unhealthy` 优先看日志里的 `db open`、`auto migrate`、`load server certificate`、`listen` 这几类错误。

认证中心管理端入口：

```text
https://你的认证中心域名/admin-ui/auth.html
```

初始只允许认证中心 `root` 用户通过客户端签名登录管理端。登录后可在“用户管理”里把其他用户设为管理员，在“系统配置”里维护注册验证码与恢复二验共用的 SMTP 授权。SMTP 只允许 `require_starttls` + 587 或 `tls` + 465，不支持明文端口。

认证中心不使用数据库配置表；`data/production/config/auth-center.hcl` 是 SMTP 配置的唯一事实来源。管理端保存 SMTP 时会直接回写该配置文件，因此 compose 里认证中心的 `auth-center.hcl` 挂载必须保持可写。

## 更新方式

更新代码或部署脚本时，保留顶层 `data/` 目录即可。可以删除并重新上传：

- `ph01-ai-gateway/`
- `ph01-backend/`
- `ph01-experience-hub/`
- `ph01-deploy/`

然后重新执行：

```bash
cd ph01-deploy/production
./deploy.sh --build
```

`data/production` 中的配置、证书、运行数据和日志不会被脚本覆盖。只有缺失文件会从新上传的 `ph01-deploy/production` 种子文件补齐。

## Nginx 反代

生产访问应统一走 HTTPS Nginx 反代。容器自身把 HTTP 端口发布到宿主机 `0.0.0.0`，反代层再对外提供 HTTPS。

### 反代目标

如果 Nginx 与 PH01 在同一台宿主机，反代目标可以继续使用：

```nginx
http://127.0.0.1:18080
http://127.0.0.1:13000
http://127.0.0.1:18090
```

如果 Nginx 在另一台机器或另一个普通 Docker bridge 容器中，反代目标应改成 PH01 宿主机 IP 加上述端口。

如果 Nginx 是同机 Docker 容器且要访问 `127.0.0.1`，需要使用 host 网络模式：

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    network_mode: host
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./certs:/etc/nginx/certs:ro
    restart: unless-stopped
```

`ph01-internal` 只用于认证中心和 AI 网关之间的内部 mTLS，不给 Nginx 使用。

### 示例配置

把下面的域名和证书路径改成实际值：

```nginx
map $http_upgrade $connection_upgrade {
  default upgrade;
  '' close;
}

server {
  listen 80;
  server_name auth.xn--lbtx0e.cn ai.xn--lbtx0e.cn experience.xn--lbtx0e.cn;
  return 301 https://$host$request_uri;
}

server {
  listen 443 ssl http2;
  server_name auth.xn--lbtx0e.cn;

  ssl_certificate     /etc/nginx/certs/auth.xn--lbtx0e.cn/fullchain.pem;
  ssl_certificate_key /etc/nginx/certs/auth.xn--lbtx0e.cn/privkey.pem;

  client_max_body_size 20m;

  location / {
    proxy_pass http://127.0.0.1:18080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 300s;
  }
}

server {
  listen 443 ssl http2;
  server_name ai.xn--lbtx0e.cn;

  ssl_certificate     /etc/nginx/certs/ai.xn--lbtx0e.cn/fullchain.pem;
  ssl_certificate_key /etc/nginx/certs/ai.xn--lbtx0e.cn/privkey.pem;

  client_max_body_size 50m;

  location / {
    proxy_pass http://127.0.0.1:13000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_buffering off;
    proxy_read_timeout 600s;
  }
}

server {
  listen 443 ssl http2;
  server_name experience.xn--lbtx0e.cn;

  ssl_certificate     /etc/nginx/certs/experience.xn--lbtx0e.cn/fullchain.pem;
  ssl_certificate_key /etc/nginx/certs/experience.xn--lbtx0e.cn/privkey.pem;

  location / {
    proxy_pass http://127.0.0.1:18090;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
    proxy_read_timeout 300s;
  }
}
```

如果经验网络治理端只给同机主脑访问，可以不配置 `experience.xn--lbtx0e.cn`，直接让主脑走 Docker 内网地址 `http://ph01-experience-network-manager:8090`。

### 防火墙要求

至少开放公网：

- `80/tcp`
- `443/tcp`

`18080/13000/18090` 默认绑定宿主机 `0.0.0.0`。如果反代不在同机，防火墙只应允许反代机器访问这三个端口；如果反代同机，建议用防火墙禁止公网直连这三个 HTTP 端口。

```bash
ufw allow 80/tcp
ufw allow 443/tcp
```

## Root 首次注册

初次部署后，最高管理员直接用子体客户端注册用户名 `root`。

认证中心的规则是：

- `root` 用户名未存在时，公开用户名预检返回可用，客户端进入注册。
- 注册用户名为 `root` 的认证中心用户会自动获得 `root` 角色。
- `root` 属于预置账号，认证中心注册阶段不会同步创建 AI 网关普通账号。
- `root` 第一次登录 AI 网关时，AI 网关会按认证中心返回的用户名绑定或创建本地 `root` 用户，并授予网关 root 权限。
- 如果认证中心里已经存在 `root`，客户端应进入登录/恢复流程，不能重复注册。

认证中心管理端登录入口：

```text
https://你的认证中心域名/admin-ui/auth.html
```

用子体客户端生成 `root` 的签名登录 JSON 后粘贴即可进入管理端。

## mTLS 文件

认证中心和 AI 网关之间走内部 mTLS：

- `data/production/certs/mtls/root-ca.pem`：内部 mTLS CA 公钥证书。
- `data/production/certs/mtls/root-ca-key.pem`：内部 mTLS CA 私钥，只用于重新签发内部证书。
- `data/production/certs/mtls/auth-center.pem`：认证中心内部 TLS 服务证书。
- `data/production/certs/mtls/auth-center-key.pem`：认证中心内部 TLS 私钥。
- `data/production/certs/mtls/ai-gateway.pem`：AI 网关客户端证书。
- `data/production/certs/mtls/ai-gateway-key.pem`：AI 网关客户端私钥。

这些文件由 `scripts/generate-mtls-certs.sh` 自动生成。AI 网关配置里的：

```yaml
ph01_auth:
  base_url: https://ph01-auth-center:8443
  ca_cert: /etc/ph01/certs/mtls/root-ca.pem
  client_cert: /etc/ph01/certs/mtls/ai-gateway.pem
  client_key: /etc/ph01/certs/mtls/ai-gateway-key.pem
  server_name: ph01-auth-center
```

对应认证中心配置里的：

```hcl
server "auth_gateway_mtls" {
  listen = ":8443"
  tls {
    cert_file           = "/etc/ph01/certs/mtls/auth-center.pem"
    key_file            = "/etc/ph01/certs/mtls/auth-center-key.pem"
    client_ca_file      = "/etc/ph01/certs/mtls/root-ca.pem"
    require_client_cert = true
  }
}
```

认证中心注册普通用户时会同步创建 AI 网关账号。同步使用 `data/production/config/auth-center.hcl` 的：

```hcl
ai_gateway_sync "default" {
  base_url       = "http://ph01-ai-gateway:3000"
  internal_token = "..."
}
```

它必须与 `data/production/config/ai-gateway.yaml` 的 `ph01_auth.internal_token` 完全一致。认证中心用户名是唯一用户名，AI 网关同步时直接使用该用户名；`root` 属于预置账号，不在注册同步阶段生成影子用户。

## 主脑访问治理端

主脑访问经验网络管控端统一走 HTTP API。

同机 Docker 容器访问：

```bash
export PH01_EXP_BASE_URL=http://ph01-experience-network-manager:8090
export PH01_EXP_TOKEN=39263fb0a04db397e36bb740852badd2cfd93f479a2f841e3f9a6c99ee11722c
```

主脑不在同一个 Docker 网络时，访问宿主机或反代域名：

```bash
export PH01_EXP_BASE_URL=https://experience.example.com
export PH01_EXP_TOKEN=39263fb0a04db397e36bb740852badd2cfd93f479a2f841e3f9a6c99ee11722c
```

治理签名接口：

```text
POST /api/v1/governance/veto_blocks/sign
Authorization: Bearer <data/production/config/experience-hub.json 中的 admin_token>
```

Root / Master 公钥证书接口可以公开读取；否决块签发接口必须带管理 token。经验网络治理不是 X.509 mTLS 体系，线上实际工作凭证是 Root 离线签发的 Master 证书与 Master 私钥。

## 经验网络密钥

经验网络不是 X.509 证书体系，使用 `secp256k1_ecdsa_sha256_rs64` 签名。

- Root 私钥：离线冷保存，不在部署目录、不进容器、不参与日常线上签名。
- Root 公钥证书：`data/production/certs/experience-network/root-certificate.json`。
- Master 公钥证书：`data/production/certs/experience-network/master-certificate.json`。
- Master 私钥：写在 `data/production/config/experience-hub.json` 的 `governance.master_private_key_hex`，这是线上实际工作密钥。
- Manifest：`data/production/certs/experience-network/manifest.json`，用于核对 Root / Master 证书指纹。

签名链路是：

```text
Root 私钥离线签发 Master 证书
  -> 经验网络管理端持有 Master 私钥
  -> 主脑发现评价链异常时请求签发 Veto Block
  -> 管理端用 Master 私钥签名 Veto Block
  -> 子体用内置 Root 公钥验证 Master 证书，再用 Master 公钥验证 Veto Block
```

Root 公钥指纹是：

```text
e051ba74936e1a651af502dafbf2eff531559fc7d60bd116b7e42740eddbab42
```

仓库根目录旧的 `secrets/generated/experience-network` 属于历史生成材料，不是服务器部署材料。部署服务器的持久材料统一放在顶层 `data/production/`；`ph01-deploy/production/config/` 和 `ph01-deploy/production/certs/` 只作为首次缺失时的种子文件。

经验网络管理端公开提供：

- `GET /api/v1/governance/root/certificate`
- `GET /api/v1/governance/master/certificate`

管理 token 鉴权后提供：

- `POST /api/v1/governance/veto_blocks/sign`

## 外部依赖边界

本 compose 只启动 PH01 三个应用容器，不启动数据库、Redis、SMTP、对象存储。生产依赖由你现有基础设施提供，并在配置文件中指定连接信息。
