# PH01 经验系统内部沟通稿

**版本**：v0.2  
**日期**：2026-05-01  
**用途**：团队内部沟通与信息同步  
**依据**：MVP v3 需求文档  

---

## 1. 一句话说明

“经验”就是一段有价值的原始经历记录。

它不是教程，不是总结，也不是 Skill 的升级版。

更准确地说：经验是一段用户和 AI 一起把问题弄清楚、做出尝试、看到结果、形成判断的原始过程。

---

## 2. 为什么不能整理成结论

如果把经验整理成结论，就会丢掉最有价值的部分。

真正有价值的往往不是一句“最后怎么做”，而是：

- 一开始为什么会这么想
- 中间哪里判断错了
- 用户如何补充背景
- AI 为什么换了方案
- 工具结果如何影响判断
- 最后结论的边界在哪里

这些过程一旦被压缩成摘要，就很难还原。

所以经验主打的是：**无损保存、可追溯、保留思路演变**。

---

## 3. 经验和 Skill 的区别

| 概念 | 简单理解 | 形式 |
|---|---|---|
| Skill | 已经整理好的做事方法 | 模板、脚本、流程 |
| 经验 | 方法产生时的完整经历 | 原始聊天记录和行为记录 |

Skill 是“怎么做”。

经验是“当初为什么会走到这个做法”。

两套系统可以并存。经验以后可以被提炼成 Skill，但经验本身不应该被做成 Skill。

---

## 4. 经验具体长什么样

经验像一段“虚拟微信聊天记录”。

但它不只包含文字对话，还包含 AI Agent 的行为：

- 用户消息
- AI 回复
- AI 的工具调用
- 命令输出
- 文件读写
- 图片、日志、附件
- 关键操作产生的结果

如果内容很长，例如大段命令输出或图片，不强行塞进聊天正文里，而是放到附件文件中，再在记录里引用。

---

## 5. 举例：Windows 密钥恢复讨论

“Windows GPU 恢复 benchmark 的经验”不是一段最终结论。

真正的经验应该是整段沟通过程：

- 用户为什么担心攻击者会逆向客户端
- 为什么需要 Windows 本机 GPU benchmark
- 我们如何讨论枚举规模和汉明距离
- 为什么认为公钥公开不是问题
- 为什么登录态应直接基于私钥
- 两阶段恢复验证是怎么逐步形成的
- 哪些假设被推翻，哪些设计被保留

这些原始过程合在一起，才是经验。

如果只留下“最终采用两阶段恢复方案”，后来的 AI 会知道结论，但不知道这个结论为什么成立，也不知道它在哪些条件下成立。

## 6. 样本目录

登录系统讨论的原始机械摘录样本放在：

`docs/experience-samples/exp_login_identity_discussion/`

该目录按经验包原型组织，样本内容使用虚拟微信单行格式保存，并用 `.md` 文件承载。文档正文不内嵌经验本体，避免把原始记录改写成摘要。

---

## 7. 脱敏怎么做

经验可以脱敏，但脱敏应发生在客户端。

流程应是：

```text
子体发现一段对话有分享价值
  -> 询问用户是否分享
  -> 用户选择完全分享、脱敏后分享、或拒绝分享
  -> 子体和用户确认哪些内容需要隐藏
  -> 在原始记录中替换敏感信息
  -> 保留原始结构和逻辑过程
```

脱敏不是改写。

例如可以把真实店铺名替换成 `[店铺名已脱敏]`，但不能把整段沟通改写成“某店铺优化了主图”。

---

## 8. 经验包的外层结构

经验包只是给原始记录加上签名、索引和评价。

```text
经验包
├── package.zip       原始聊天与行为转储
├── publisher.json    发布者和签名材料
└── ratings.dat       评价链
```

其中 `package.zip` 才是经验本体。

索引、签名、评价都是外层治理信息，不能替代原始记录。

---

## 9. 管理端的定位

经验管理端部署在大容量服务器上。

它负责保存经验包、维护索引、支持审核和下载。

它不负责把经验整理成文章。

主脑通过 CLI 或文件系统式视图读取经验时，应该看到的是原始记录和附件，而不是一篇经过加工的“经验正文”。

---

## 10. 为什么暂不把 RAG 当第一入口

RAG 或向量检索可以以后再加。

但它不应该成为经验的本体，也不应该替代原始记录。

更关键的是，主脑本身是 AI Agent。它可以像开发者看项目一样看经验库：

```text
先看目录
  -> 看 README / metadata
  -> 用关键词全文搜索
  -> 打开 conversation.md 的相关片段
  -> 继续追溯上下文、工具输出和附件
```

所以当前更适合先做：

- 可读目录名
- README 和 metadata 路标
- 文件内容搜索
- 原始记录片段读取
- 附件和工具结果追溯
- 评价排序

这样团队能清楚检查某条经验为什么被命中，主脑也能追溯完整过程。

数据库、全文索引、embedding 可以作为后台加速层，但不应该成为主脑唯一能看到的入口。经验库首先应当像一个可阅读、可搜索、可追溯的文件系统，而不是一个只吐召回片段的黑盒检索服务。

---

## 11. 团队讨论重点

后续讨论建议围绕这些问题：

1. 子体如何判断一段对话值得分享
2. 用户如何确认脱敏范围
3. 原始聊天记录和工具调用如何完整导出
4. 附件、图片、日志如何引用
5. metadata 最少需要哪些字段
6. 审核签名链如何落地
7. 经验管理端是否需要后台索引加速，以及如何保证文件系统式入口不变

---

## 12. 当前结论

当前方向应固定为：

- 经验本体是原始记录
- 只做脱敏，不做整理
- Skill 与经验并存
- 经验可以成为 Skill 的来源
- 管理端保存包和索引
- 主脑通过文件系统式视图读取原始过程
- RAG / 向量 / 数据库只能作为后台加速，不作为经验本体
- MVP v3 是最高准则
