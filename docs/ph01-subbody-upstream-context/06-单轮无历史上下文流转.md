场景假设：

- 用户输入：`{user_prompt}`
- 没有任何历史对话
- 当前 Agent：`仙灵 (eca192de)`
- 当前工作目录：`C:\Users\dream\AppData\Roaming\hanako\agents\eca192de\desk`
- AI 网关启用 `MarkdownASTToolCallsEnabled`

## 一、首次进入上游模型

上游模型第一次看到 3 个上下文块，顺序如下。

### 1. system：AI 网关工具协议

这段由 AI 网关插入，完整正文见 [04-网关抽象语法树工具提示词.md](./04-网关抽象语法树工具提示词.md)。真实请求中会把 04 的正文作为第一条 system 消息传给上游模型。

## 二、如果模型决定调用工具

模型不会输出 JSON，也不会输出 provider 原生 `function_call`。

它直接输出 Markdown AST 工具块，例如：

```text
<----工具调用开始：read---->
# max_chars
20000

# path
{file_path}

<----工具调用结束---->
```

这段内容会被网关识别成工具调用，再转回子体可执行的原生工具调用。

## 三、工具返回后再次进入上游模型

工具执行完成后，下一轮上游模型看到的上下文顺序如下。

### 1. system：AI 网关工具协议

与首次进入上游模型时完全相同，内容见 04。

### 2. system：子体系统提示词

与首次进入上游模型时完全相同，内容见 01。

### 3. user：原始用户输入

```text
{user_prompt}
```

### 4. assistant：上一轮工具调用

```text
<----工具调用开始：read---->
# max_chars
20000

# path
{file_path}

<----工具调用结束---->
```

### 5. user：工具返回块

```text
<----工具返回开始：read---->
# status
success

# tool_call_id
{tool_call_id}

# content
{tool_result_content}
<----工具返回结束---->
```

如果工具本身输出了 JSON，那只是工具输出文本，不是请求体。

## 四、循环关系

如果模型继续调用工具，就重复下面这条链路：

1. 模型输出工具调用块。
2. 网关转成原生 tool call。
3. 子体执行工具。
4. 工具返回块作为 user 上下文进入下一轮。
5. 模型根据新上下文继续输出，或结束回答。
