# Flutter 跨端高刷稳定性复盘（2026-02-07）

## 1. 目标与结论

- 目标：解释“为什么之前卡、为什么现在不卡”，并沉淀成可复用的跨项目排障方法。
- 结论：本次问题的核心不是 Flutter 框架性能，而是**各端刷新率/显示链路没有被正确驱动**。
- 结论：在根因修复后，即使切换为昂贵视觉方案，Windows 与 Android 仍能维持高刷区间，说明修复方向正确。

---

## 2. 现象复盘

### 2.1 初始现象

- Android 设备是高刷屏，但应用视觉上接近 60fps。
- Windows 端曾出现明显低帧体感，甚至接近 30fps 的不可接受状态。
- 当时页面并非极端复杂，这与“纯 UI 过重导致掉帧”的常识不完全一致。

### 2.2 误判风险

- 只盯 Flutter 页面层（动画、透明、模糊）会导致“越改越偏”。
- 若不先确认系统刷新率投票和显示链路状态，就会把根因与症状混淆。

---

## 3. 诊断方法（先定位根因，再谈优化）

### 3.1 三层观测法

- 系统层：刷新率投票、显示模式是否真到 120Hz。
- 引擎层：profile 模式下 `fps/build/raster` 关系。
- 页面层：是否存在高成本渲染（模糊、半透明叠层、持续动画）。

### 3.2 关键判据

- 如果 `build/raster` 不高但 fps 仍被锁低，优先怀疑系统策略限制。
- 如果 `build/raster` 同时升高，才是页面复杂度或渲染路径压力。

---

## 4. 根本根因（重点）

## 4.1 Android 根因：刷新率投票链路把应用约束在 60Hz

修复前通过 `adb shell dumpsys display` 可见：

- `appRequest ... render` 为 `60.000004`
- `PRIORITY_APP_REQUEST_BASE_MODE_REFRESH_RATE` 为 `60.000004`
- `PRIORITY_APP_REQUEST_RENDER_FRAME_RATE_RANGE max` 为 `60.000004`

这表示：

- 设备支持 120Hz，但应用“请求值”仍是 60Hz。
- 系统调度按 App Request 投票，最终把应用渲染上限压在 60。

这就是手机端“看起来不流畅但 build/raster 又不高”的根本原因。

## 4.2 Windows 根因：显示链路/设备选路不稳定，而非 Flutter 页面必然卡

Windows 的核心不是“页面复杂必掉帧”，而是以下链路因素：

- GPU 选路不稳定（混合显卡环境可能走到非高性能路径）。
- 系统显示链路干扰（虚拟显示驱动、远程桌面链路、显示复制路径）。
- 平台线程与 UI 线程调度耦合造成抖动。

为什么判断这才是根因：

- 同一 Flutter 页面在 Web profile 能高帧。
- Windows profile 中 `build/raster` 远低于预算时也可高帧。
- 说明“Flutter 页面复杂度”不是 Windows 低帧的决定因素。

## 4.3 页面昂贵效果的定位

- 昂贵效果会提高 `raster` 压力，是“放大器”。
- 但在本次问题里，它不是导致“被锁低刷”的根因。
- 根因修复后，即使增加昂贵效果，帧率依然可进入高刷区间。

---

## 5. 修复方案与生效机理

## 5.1 Android：主动申请同分辨率最高刷新模式

模块：安卓启动入口（`MainActivity`）

实施：

- `onCreate` / `onResume` 均执行刷新模式申请。
- 从 `supportedModes` 过滤当前分辨率，选择最高 `refreshRate` 对应 `modeId`。
- 写入 `window.attributes.preferredDisplayModeId`。

机理：

- 显式把应用刷新率请求抬到 120Hz，系统投票链路跟随更新。

## 5.2 Android：固定渲染后端一致性

模块：安卓清单配置

实施：

- 启用 Impeller（Vulkan）。

机理：

- 降低设备/驱动差异造成的渲染路径波动。

## 5.3 Windows：提高显示链路稳定性

模块：Windows 启动器

实施：

- 导出 `NvOptimusEnablement=1`、`AmdPowerXpressRequestHighPerformance=1`。
- 设置 `UIThreadPolicy::RunOnSeparateThread`。

机理：

- 显式偏好高性能 GPU，降低错误选路概率。
- 减少平台线程与 UI 线程互相挤占导致的帧抖动。

## 5.4 统一观测：内置 PerfHUD

模块：Flutter 主页面

实施：

- 实时输出 `FPS / build / raster`。
- FPS 基于 `FramePhase.vsyncStart` 间隔计算。

机理：

- 统一跨端判断口径，避免“体感讨论”缺乏数据支撑。

## 6. 压力测试（昂贵设计回归）

## 6.1 压测目的

- 验证根因修复后，系统能否在“高成本视觉负载”下仍保持高刷。
- 避免把“轻量 UI 下的高帧”误当成修复成功。

## 6.2 压测场景

- 全局动态多层背景。
- 多层模糊与半透明玻璃态叠加。
- 滚动过程 3D 变换 + 连续自动翻页。

说明：该场景是故意昂贵，用于压测上限，不代表业务默认方案。

## 6.3 Windows 压测结果

采样（profile）统计：

- `count=64`
- `fps_avg=184.3`
- `fps_p5=180.0`
- `fps_p95=194.8`
- `fps_min=138.8`
- `fps_max=200.2`
- `build_avg=0.28ms`
- `raster_avg=1.99ms`

结论：

- 高刷稳定，窗口端已不再出现“被压到 30fps”的异常状态。
- 少量低点属于瞬时波动，不影响总体高刷表现。

## 6.4 Android 压测结果

采样（profile）统计：

- `count=46`
- `fps_avg=110.6`
- `fps_p5=100.5`
- `fps_p95=119.5`
- `fps_min=96.1`
- `fps_max=119.6`
- `build_avg=0.87ms`
- `raster_avg=6.87ms`

系统状态：

- `dumpsys display` 显示 `appRequest render` 与 `baseMode` 为 `120.00001`。

结论：

- 手机端处于高刷区间，存在一定 low 帧属于移动端 GPU 预算差异下的正常现象。
- 与 Windows 相比低点更多，符合硬件性能差异与场景成本差异预期。

---

## 7. 为什么现在没问题

- Android：修复了“刷新率投票被锁 60”的核心约束。
- Windows：修复了“显示链路/设备选路不稳定”导致的异常低帧风险。
- 页面层：即使压力场景增加昂贵效果，在根因修复后仍能保持高刷区间。

这说明本次提升不是“删特效换流畅”，而是先解决系统级限制，再做页面级优化。

---

## 8. 昂贵操作优化建议（可选）

> 下列建议用于控制成本，不是本次根因修复的替代品。

- 模糊：优先局部模糊，避免全屏持续 `BackdropFilter`。
- 透明：减少多层半透明叠加，能不透明就不透明。
- 动画：滚动期优先“静态内容 + 必要反馈”，重动画放到切换结束后。
- 重绘：对稳定区域加 `RepaintBoundary`，隔离不必要重绘传播。
- 采样：固定用 profile + `fps/build/raster` 联合判定，不凭肉眼单点判断。

---

## 9. 跨项目复用清单

1. 先查系统刷新率投票是否真的到高刷。  
2. 再查 `build/raster` 判断瓶颈在线程还是 GPU。  
3. 最后才做 UI 结构优化与特效取舍。  
4. 每次改动都保留同口径压测样本（常规场景 + 压力场景）。

---

## 10. 命令化排查模板

## 10.1 Android（真机）

- 查看系统是否给到高刷请求：
  - `adb shell dumpsys display | findstr /I "appRequest render BaseModeRefreshRateVote"`
- 启动 profile 并观察应用日志：
  - `flutter run -d <deviceId> --profile`
  - 关注 `PerfHUD` 的 `fps/build/raster`
- 快速判断：
  - `appRequest render` 仍是 60：先修系统请求链路（`preferredDisplayModeId`）
  - `appRequest render` 已是 120，但 `raster` 持续很高：再优化页面渲染成本

## 10.2 Windows（桌面）

- profile 模式运行：
  - `flutter run -d windows --profile`
- 观察 `PerfHUD`：
  - `build` 低、`raster` 低但体感卡：优先排查显示链路/显卡选路
  - `raster` 高：优先排查模糊、透明叠层、持续动画
- 环境排查建议：
  - 避免远程桌面链路做性能结论
  - 避免虚拟显示驱动干扰结论
  - 固定高性能电源策略后再采样

## 10.3 压测与验收建议

- 常规场景与压力场景都测，避免“轻载通过、重载失真”。
- 至少记录：
  - fps 平均值
  - p5/p95
  - build/raster 平均值
  - 系统刷新率请求字段（Android）

## 11. 关键代码定位

- 安卓刷新模式申请：`android/app/src/main/kotlin/com/example/angel_motion_showcase/MainActivity.kt`
- 安卓渲染后端配置：`android/app/src/main/AndroidManifest.xml`
- Flutter 帧监测与压测场景：`lib/main.dart`
- Windows 启动器策略：`windows/runner/main.cpp`

---

## 12. 维护注意项

- Windows profile 日志会提示“unmerged platform and UI threads 将在未来移除”。
- 含义：`RunOnSeparateThread` 未来可能失效或需替代方案。
- 建议：升级 Flutter 版本时，优先复测 Windows 帧稳定性，并关注官方 Windows embedder 线程策略变更。
